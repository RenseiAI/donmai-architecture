# Donmai Architecture

Canonical OSS architecture corpus for the **Donmai execution layer** — the `donmai` binary, the local daemon (`donmai daemon`), the runner, the eight Provider Families, the Kit composition framework, and the workflow engine that underlies them.

This corpus is the single source of truth for cross-repo architectural decisions affecting the OSS execution layer. Where any project's documentation conflicts with what's written here, this wins.

## What lives here vs. its sibling

This repository is the **OSS-public canonical corpus**. Its sibling, [`rensei-architecture`](https://github.com/RenseiAI/rensei-architecture), is the **Rensei-Platform-extensions corpus** — it carries the platform-only docs (Linear realignment against the Rensei team's backlog, PM agent definitions tied to that backlog, the SaaS dashboard parity discipline, multi-tenant control-plane decisions) and the platform-side `<doc>-platform-extensions.md` deltas that extend shared docs in this repo.

The boundary discipline — verbatim from `001-layered-execution-model.md` § "The donmai ↔ Rensei Platform contract":

> 1. The OSS layer defines all interfaces in this corpus.
> 2. The OSS layer ships a working implementation of every interface — never *only* the type.
> 3. The SaaS control plane extends with alternate implementations and centralized administration (registries, signing, policy enforcement, multi-tenant management, the SaaS dashboard, the routing-intelligence panel).
> 4. The OSS layer never depends on the SaaS plane to function. Removing the platform leaves a usable single-machine product.
> 5. The boundary between them is a small set of pluggable function callbacks (`setAgentLauncher`-shaped), not subprocess or RPC. The platform composes the OSS layer as a library; both ship as one binary to end users.

That discipline — particularly point (4), "removing the platform leaves a usable single-machine product" — is what determines which docs live in this corpus and which extend the contract from `rensei-architecture`. See `BOUNDARY.md` for the convention this repo uses to keep the split honest going forward.

- **`ADR-2026-08-12-placement-composition-law-and-single-fallback-rule.md`** — **Accepted.** Six separately Accepted decisions each described *an* authority over placement; none described the order of authorities, and the gap produced four live contradictions. This ADR states the **composition law**: six stages — intent, permission, viability, preference, ranking, bind — each holding exactly one kind of power, with power monotone down the list (no stage adds a candidate an earlier stage removed; no stage substitutes a target that was never a candidate). The stage order is an **authority** order, not an evaluation order; what it fixes is attribution, so a candidate excluded by more than one stage is reported at the earliest stage that excludes it. **D1** details the stages: permission is fail-closed with deny monotone downward and **allow-merge as intersection** (product-owner ruling — the auditable fork, whose sharp edge is recorded), obligations discharged at bind or the bind fails; viability is the **full tuple** — model × harness × auth binding × kit/toolchain demands × execution-host capabilities × lane × serving endpoint × health × requested mode — whose **∅ is always loud and typed**, naming every candidate and the stage and rule that excluded it, including candidates that are viable but unpermitted; preference orders and narrows and never widens, with a **pin hard within the law** (a non-surviving pin fails loudly with the pin named, so `strictPinMode` is retired — there is no non-strict pin); ranking **orders and does nothing else**, with the candidate set as the failover set and the learning payload written at decision time or forfeited; bind is the cell ADR's intersection plus obligations, with a narrow-only claim re-gate and separate receipts. **D2 — one fallback rule:** the next candidate in the ordered surviving set, already permitted and already viable; out-of-set substitution never happens; the separately authored fallback list is retired; escalation beyond the set is a **permission** question re-entering at stage 1 with the posture declared on the profile, and predictive escalation stays undesigned. **D3** reconciles the double-booked ranking authority: `004`'s unscored first-in-declared-order becomes the **default ordering policy** of a capacity profile (the only one the OSS layer implements), richer ordering policies are a hosted extension point, ordering may never gate, and `004`'s three preserved reasons are each answered rather than cited — including the load-ratio inversion, inherited verbatim as a precondition. **D4** rules the inference-host axis (`hosts[]`) a **viability input, not a placement kind**: `PlacementRef.kind` stays closed, and the two referents of `host` (execution host / inference host) are qualified in prose rather than renamed. **D5** fixes the vocabulary — placement / selection / steering / **control flow** (the DAG sense) — and settles the standing boundary-precedent conflict: **the law and the vocabulary are shared** because the OSS daemon already decides and explains its own placements, while **the concrete resolver mechanics stay downstream** because no OSS implementation of them exists or will. **D6** defines one decision-record shape everywhere, seeded by the daemon's existing `RoutingDecision`/`RoutingTraceStep` wire, with bounded and exposed staleness on every record. Amends `001` (Layer 3 building blocks, Layer 4 toolchain-demand seam), `004` (routing-algorithm steps 4–5, the per-session-scorer rebuttal, open question 2, ownership table), `013` (dispatch item 4, routing-around, ownership table), and carries forward annotations on `ADR-2026-08-05` D3, `ADR-2026-08-07` D6.2/D7, and `ADR-2026-06-14` — all edits landed in the accepting commit, alongside three new `retired-claim-lint.sh` rules. ## How this corpus changes

This repo follows permissive-direct-to-main norms. Both humans and fleet agents may commit directly. The git history is the audit log.

**Substantive architectural changes follow the ADR pattern**: copy `ADR-template.md` to a new dated file (named `ADR-YYYY-MM-DD-<slug>.md`), commit the proposal, and update the affected reference docs in the same commit. The canonical doc (`001`) is updated only when an ADR has shifted the layered model itself. New ADRs declare a `boundary:` field in their frontmatter — see `BOUNDARY.md`.

**Non-substantive edits** (typos, clarifications, examples, broken-link fixes) commit directly without ceremony.
